Runtime configuration

The image should be boring: build it once, and let it move through development, test and production unchanged. Everything that varies by environment — hosts, secrets, storage, network shape, how much CPU it is allowed — is supplied when the container starts, not baked into the artefact. This talk is that boundary, worked through eight times.

The route

Eight runtime knobs, one image underneath all of them

1

Section one

Configuration belongs
outside the image

One Flask image, built once. Everything that changes between your laptop, test, and production — database host, secret key, which environment it thinks it's in — arrives through the container, not the build.

The distinction the whole talk rests on

The image never changes. What you inject into it does.

The Flask app

Reads DB_HOST, DB_PORT, DB_NAME, DB_USER, APP_SECRET_KEY and APP_ENV from the environment at request time — never from a config file baked into the image.

The deliberate detail

/config reports every value except the secret key — it returns app_secret_key_configured: true instead. Configured, never echoed.

ENV is for safe defaults, not for facts that vary

A default you can ship. A fact you cannot.

# Dockerfile — safe, boring, the same for everyone ENV PYTHONUNBUFFERED=1 \ APP_HOME=/app \ APP_ENV=production \ PORT=8000 # none of this is a secret, and none of it needs # to differ between two copies of the same image
Safe as an image default

PYTHONUNBUFFERED, PORT, a fallback APP_ENV — values every deployment agrees on, or values it's fine to override.

Never a safe image default

DB_HOST, DB_NAME, DB_USER, and above all APP_SECRET_KEY — these differ by environment and must arrive at docker run, not docker build.

The rule

ENV is useful for defaults. It is not a vault. Anything written into the image config is visible to anyone who can pull the image or read docker inspect.

Cue · ask the room to name one value in their own services that is currently a build-time default but should really be runtime-only. There is usually at least one.

Demo 1 · four beats

Build the image once. Configure it at the door.

1

Build with no certificate and no secret. It succeeds — the corporate CA hook is present but idle on a normal laptop.

$ DOCKER_BUILDKIT=1 docker build -t talk-02-runtime-config . => exporting to image => naming to docker.io/library/talk-02-runtime-config DONE
2

Run it once, with a full set of inline -e flags for a development-shaped container.

$ docker run -d --rm --name runtime-inline -p 8000:8000 \ -e DB_HOST=host.docker.internal -e DB_PORT=5432 -e DB_NAME=myapp \ -e DB_USER=myuser -e APP_SECRET_KEY=runtime-secret -e APP_ENV=development \ talk-02-runtime-config
3

/health reports every required variable present; /config proves the secret is configured without ever printing it.

$ curl http://localhost:8000/health {"status": "ok", "missing": [], "environment": "development"} $ curl http://localhost:8000/config {"db_host": "host.docker.internal", "db_port": 5432, "db_name": "myapp", "db_user": "myuser", "app_env": "development", "app_secret_key_configured": true} ↑ configured, never echoed
4

Stop it. The image is untouched by anything that just happened.

$ docker stop runtime-inline

Cue · narrate beat 2 out loud as you type it — every -e is a fact the image did not know at build time. That is the whole section, made concrete.

2

Section two

Same mechanism,
two shapes of ergonomics

-e and --env-file both do the same thing — hand the container facts at start-up. One is explicit and painful at scale; the other is reviewable and reusable.

Three related things, easy to conflate

Explicit, maintainable, and safe-to-commit are three different jobs

Inline · -e

One flag per variable, right there in the command. Great for a demo, or one override — docker run -e APP_ENV=development … — but a six-variable command is hard to read and easy to typo.

Grouped · --env-file

All the variables live in one reviewable file: docker run --env-file .env …. Easier to diff, easier to reuse across a team, and it is what a real deployment actually looks like.

Sample vs real · .env.example / .env

.env.example is safe sample configuration, committed to the repo. The real .env — with an actual secret key — stays local and gitignored, never committed.

Cue · this is a good moment to ask who in the room has a .env sitting in a repo right now. It happens even to careful teams, and it's why .env.example exists as the pattern to copy from, not from a real file.

Demo 2

The maintainable version, exercised against a real endpoint

$ docker run -d --rm --name runtime-env-file -p 8000:8000 --env-file .env talk-02-runtime-config $ curl http://localhost:8000/items {"items": [ {"id": 1, "name": "container-basics", "description": "Recap from Talk 1"}, {"id": 2, "name": "runtime-config", "description": "Configuration is injected at runtime"} ], "count": 2, "database_target": "postgresql://myuser@localhost:5432/myapp"} $ curl -X POST http://localhost:8000/items \ -H 'Content-Type: application/json' \ -d '{"name":"demo item","description":"created during the talk"}' {"id": 3, "name": "demo item", "description": "created during the talk"}

Cue · point at database_target in the GET response — it's built entirely from env-file values, and swapping .env for a different file is the entire migration story between environments. No code change, no rebuild.

3

Section three

ARG is metadata.
--secret is scoped. Neither is a vault.

A BuildKit secret mount keeps a credential out of every layer — but it only solves the problem of the build needing access to something. The running container still needs its own, separate delivery.

Follow APP_VERSION and a build secret across the same boundary

What crosses into the image, and what a build secret never solves

Expert aside · BuildKit --mount=type=secret does not copy the secret into the build context or commit it to a layer. The risk returns only if the build step itself writes the secret to the filesystem, logs it, or bakes it into a generated artefact.

Demo 3 · two beats

Mount a build secret, then check it never became a layer

1

Rebuild with a BuildKit secret supplying secret.txt to the one RUN step that asks for it.

$ DOCKER_BUILDKIT=1 docker build --secret id=mysecret,src=secret.txt -t talk-02-runtime-config . => [6/8] RUN --mount=type=secret,id=mysecret,required=false … DONE
2

Inspect the full, untruncated history. The secret's contents appear nowhere.

$ docker history --no-trunc talk-02-runtime-config | head CREATED BY SIZE CMD ["gunicorn" "--chdir" "src" …] 0B HEALTHCHECK &{["CMD-SHELL" "curl --fail --silent …"] "30s" …} 0B EXPOSE map[8000/tcp:{}] 0B USER appuser 0B RUN useradd --create-home … && chown -R appuser:appuser /app 1.1kB COPY src ./src 20.4kB RUN |1 BUILDKIT_MOUNT… /bin/sh -c 'if [ -f /run/secrets/mysecret ]… 0B ↑ no "super-secret-api-key" anywhere in this output

Cue · the Dockerfile's own comment is honest about this being a demo pattern — cat /run/secrets/mysecret > /tmp/secret_used.txt && rm -f /tmp/secret_used.txt inside one RUN. It's contrived on purpose, so the mechanism is unmistakable. required=false means the build also succeeds cleanly with no --secret at all — try it, and it just prints "No build secret supplied".

4

Section four

A container always gets
its own network namespace

What changes across bridge, user-defined bridge, host, and none is not whether there is a boundary — it's what that boundary lets the container see.

The mode you pick decides what "localhost" and a container's name even mean

Only one of these four gives you DNS by name

Demo 4 · three beats

Prove name-based discovery, then show the two boundary cases

1

A user-defined bridge, and a BusyBox container that finds the API by name alone.

$ docker network create mynetwork $ docker run -d --rm --name runtime-api --network mynetwork --env-file .env -p 8000:8000 talk-02-runtime-config $ docker run --rm --network mynetwork busybox:1.36 ping -c 1 runtime-api PING runtime-api (172.19.0.2): 56 data bytes 64 bytes from 172.19.0.2: seq=0 ttl=64 time=0.087 ms ↑ resolved by name — Docker's embedded DNS, not /etc/hosts
2

Host networking — call out the Docker Desktop VM caveat as you run it.

$ docker run -d --rm --name host-network-demo --network=host --env-file .env talk-02-runtime-config ↑ on Docker Desktop, mediated by the VM; on native Linux, direct
3

--network=none — the process starts, and network assumptions surface immediately in the logs.

$ docker run -d --rm --name no-network-demo --network=none --env-file .env talk-02-runtime-config $ docker logs no-network-demo | tail -n 5 [gunicorn] worker booted — listening on 0.0.0.0:8000 (no route beyond loopback)

Cue · tear the network down after beat 1 — docker stop runtime-api; docker network rm mynetwork — before moving to host/none so the port isn't double-bound.

5

Section five

Three ways to keep a file,
with three different owners

Bind mount, named volume, and tmpfs all show up as an ordinary path inside the container. Their ownership, backup story, and lifecycle are not remotely the same thing.

Same-looking path, three different lifecycles

Ask "who owns this, and when does it disappear?"

Expert aside · bind mounts expose a specific host path, named volumes live under the engine's own managed storage, and tmpfs never writes to the container's writable layer at all. Three different backing stores wearing the same -v-shaped syntax.

Demo 5 · three beats

Write the same kind of file three different ways

1

Bind mount — the file lands directly on the host.

$ mkdir -p data $ docker run --rm --env-file .env -v "$(pwd)/data:/app/data" talk-02-runtime-config \ python -c 'from pathlib import Path; Path("/app/data/bind.txt").write_text("bind mount")' $ cat data/bind.txt bind mount ← written straight onto this machine
2

Named volume — no host path to remember or clean up by hand.

$ docker volume create mydata $ docker run --rm --env-file .env -v mydata:/app/data talk-02-runtime-config \ python -c 'from pathlib import Path; Path("/app/data/volume.txt").write_text("named volume")' ↑ lives under Docker's managed storage instead
3

tmpfs — gone the moment this container exits.

$ docker run --rm --env-file .env --tmpfs /tmp:size=100m talk-02-runtime-config \ python -c 'from pathlib import Path; Path("/tmp/tmpfs.txt").write_text("tmpfs")' ↑ never touched disk; already gone now the container has stopped

Cue · after beat 3, try to cat the tmpfs file from a fresh container mounting the same path — there is nothing there. That absence is the entire point, made visible.

6

Section six

"Running" and "ready"
are different claims

A PID existing tells you almost nothing about whether the application can serve useful traffic. HEALTHCHECK is how the container engine tells the two apart.

This Dockerfile's own HEALTHCHECK line

starting → healthy or unhealthy, on a schedule you set

Demo 6 · two beats

Read state off the container, not off a guess

1

Start it, wait past the start-period, then ask Docker for the health state directly.

$ docker run -d --name health-demo --env-file .env -p 8000:8000 talk-02-runtime-config $ sleep 35 $ docker inspect --format='{{json .State.Health}}' health-demo {"Status":"healthy","FailingStreak":0, "Log":[{"ExitCode":0,"Output":"{\"status\": \"ok\", \"missing\": []}\n"}]} ↑ container state, not just a running PID
2

A restart policy is a separate, engine-level setting — check it the same way.

$ docker run -d --name restart-demo --restart=unless-stopped --env-file .env talk-02-runtime-config $ docker inspect --format='{{.HostConfig.RestartPolicy.Name}}' restart-demo unless-stopped

Cue · stop health-demo and restart-demo with docker rm -f before moving on — both are long-running (no --rm), unlike most of the earlier demos.

7

Section seven

The same two kernel
features from Talk 01, back again

Namespaces limit what a process can see; cgroups limit what it can consume. --memory and --cpus are how you set those caps without touching a line of code.

A limit is a promise to every other container on the host

Exceed the memory cap, and the kernel ends the conversation

Expert aside · without limits, one noisy container can degrade the entire host — memory pressure and CPU starvation are shared-neighbour problems, not per-container ones. Limits make failure predictable instead of contagious.

Demo 7

Cap it, and watch nothing about the image need to change

$ docker run --rm --env-file .env --memory=256m --cpus=0.5 talk-02-runtime-config \ python -c 'import os; print("limited container pid", os.getpid())' limited container pid 1 ↑ same process, same image — now capped, no rebuild needed

Cue · if you have a moment to spare, deliberately allocate past 256 MB in a throwaway Python one-liner and let the room watch the container exit with code 137 — seeing the OOM kill happen live lands harder than describing it.

Section eight · the bonus corner

Same CLI shape.
No daemon. No root, by default.

Podman's day-to-day commands are intentionally Docker-compatible — the two things that actually changed are the daemon and the privilege model.

Familiar commands, different architecture underneath

Podman removes the always-on, usually-root daemon entirely

Expert aside · rootless Podman reduces dependence on a privileged central daemon. It does not remove every kernel-level risk, but it narrows the blast radius of a compromised container process because it runs under an unprivileged user namespace rather than as root.

Demo 8 · bonus

Run the comparison script and land on pods

$ bash bonus/podman-comparison.sh Podman vs Docker quick comparison Podman is daemonless and supports rootless containers as a first-class workflow. Many day-to-day commands are intentionally Docker-compatible. podman run --rm -p 8000:8000 --env-file .env talk-02-runtime-config podman build -t talk-02-runtime-config . podman push talk-02-runtime-config quay.io/example/talk-02-runtime-config:latest # unique to Podman — pods: podman pod create --name runtime-config-pod -p 8000:8000 podman run -d --pod runtime-config-pod --env-file .env talk-02-runtime-config # the bridge to Kubernetes: podman generate kube runtime-config-pod > podman-generated-pod.yaml

Cue · pause on the last two lines — a pod grouping containers under one shared network namespace is precisely the Kubernetes concept Talk 12 spends an hour on. Podman unavailable? skip straight to reading the script's output and explain the rootless/daemonless ideas from the speaker guide instead.

Over to you

Five questions worth arguing about

01 · boundaries

Which configuration values in your own services are safe image defaults, and which must be runtime-only?

02 · accountability

If a secret ever appears in docker history, what process actually failed — build design, review, or CI policy? Or all three?

03 · trade-offs

When would you choose a bind mount over a named volume, despite the host coupling it creates?

04 · operations

What does your platform actually use health checks for — readiness, restart decisions, load balancing, or release gates?

05 · incidents

How would your team explain the difference between Docker Desktop host networking and native Linux host networking, mid-incident?

Cue · 02 and 05 tend to generate the most disagreement, so hold them in reserve if the room is quiet. If nobody bites on 03, offer the concrete case: a debugging session where you want to see the file land on your own disk immediately.

The close

Six things to leave with

  • 01Build one reusable image and inject environment-specific configuration when the container starts — never rebuild for a config change.
  • 02ARG and ENV are not secret stores. BuildKit secret mounts are safer for build-time credentials, but they do not solve runtime secret management.
  • 03A user-defined bridge network gives local containers useful DNS-based service discovery — the default bridge does not.
  • 04Bind mounts, named volumes, and tmpfs are different lifecycle choices, not interchangeable -v syntax.
  • 05Health checks, restart policies, and resource limits are what turn a running container into an operable service.
  • 06Podman is close enough for most Docker workflows day to day — rootless and daemonless are the real architectural differences underneath.
If only one sentence survives the week

The runtime contract is where operations, security, and portability meet: everything this talk covered was really just a different answer to "what does the container need to be handed at start-up, and by whom?"

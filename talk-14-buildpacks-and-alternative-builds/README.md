# Cloud Native Buildpacks & Alternative Build Tools

Talk 14 explores how to build container images without hand-writing Dockerfiles for every application. The main demo uses a Ruby/Sinatra API, then contrasts that workflow with `ko`, Jib, and Nixpacks.

## Prerequisites

- Talks 1-13 from this series
- Docker Desktop or another local Docker runtime
- [pack CLI](https://buildpacks.io/docs/install-pack/)
- [ko](https://ko.build/)
- Node.js and npm
- Go 1.22+
- Java 17+
- Maven 3.9+

## Talk outline (~60 minutes)

1. **The problem with Dockerfiles**: boilerplate, security mistakes, and no shared standards
2. **Cloud Native Buildpacks (CNB) overview**: builders, buildpacks, lifecycle, and OCI images
3. **`pack build` CLI**: auto-detect language and build without a Dockerfile
4. **Builder images**: compare Heroku, Paketo, and Google builders
5. **Buildpack rebase**: update OS layers without rebuilding app code
6. **Built-in SBOMs**: inspect dependencies and layers generated by buildpacks
7. **`ko` for Go**: build minimal images without Docker or a Dockerfile
8. **`jib` for Java**: Maven/Gradle plugin, layered builds, and no Docker daemon requirement
9. **Nixpacks**: Heroku-like experience for many languages
10. **Comparison**: Dockerfile vs Buildpacks vs ko vs Jib vs Nixpacks
11. **When to use each**: balancing control, standards, repeatability, and convenience

## Why move beyond Dockerfiles?

Dockerfiles are powerful, but teams often copy-paste the same setup for every app:

- Installing language runtimes manually
- Repeating dependency caching tricks
- Forgetting non-root users
- Shipping large or unpatched base images
- Having no standard place for SBOMs or metadata

Alternative build tools reduce that repetition by encoding best practices into the build system itself.

## Main demo: Cloud Native Buildpacks with Ruby / Sinatra

The `ruby-app` directory contains a complete Sinatra API with:

- `/` for app information
- `/health` for health checks
- `/items` for listing and creating items
- `Procfile` so platforms understand the launch command
- `config.ru` for Rack compatibility

### Run locally with Ruby

```bash
cd ruby-app
bundle install
bundle exec ruby app.rb
```

What this shows:
- You can run the app normally before containerizing it
- Buildpacks detect Ruby from `Gemfile` and `Gemfile.lock`
- The app binds to `0.0.0.0` and respects `PORT`, which is container friendly

### Build with Paketo buildpacks

```bash
cd ruby-app
pack build ruby-sinatra-app \
  --builder paketobuildpacks/builder-jammy-base:latest \
  --env PORT=4567
```

What this does:
- Detects the app as Ruby automatically
- Installs the right runtime and dependencies
- Produces an OCI image without any Dockerfile
- Applies standardized build and launch layers

### Run the buildpack image

```bash
docker run --rm -p 4567:4567 -e PORT=4567 ruby-sinatra-app
curl http://localhost:4567/health
```

Why it matters:
- Same image format as Docker-built images
- Easier onboarding because the build command is standardized
- Great for platform teams who want safe defaults

### Try different builder images

```bash
pack build ruby-sinatra-heroku \
  --path ./ruby-app \
  --builder heroku/builder:24 \
  --env PORT=4567

pack build ruby-sinatra-google \
  --path ./ruby-app \
  --builder gcr.io/buildpacks/builder:v1 \
  --env PORT=4567
```

This is useful for showing:
- Builders package different stacks, buildpacks, and opinions
- You can swap builders without changing application code
- Platform choice becomes configuration, not hand-written Docker logic

### Inspect buildpack metadata and SBOMs

```bash
pack inspect-image ruby-sinatra-app
pack sbom download ruby-sinatra-app --output-dir ./sbom-output
```

Why this matters:
- Buildpacks emit metadata automatically
- SBOMs improve software supply chain visibility
- Security teams can inspect components without reverse engineering an image

### Rebase to update OS layers

```bash
pack rebase ruby-sinatra-app
```

What rebase means:
- Replace the base run image layers with patched ones
- Keep the application layers intact
- Avoid a full rebuild when the app code did not change

This is one of the strongest CNB features for fast security patching.

## Alternative tool: `ko` for Go

The `go-app` example is designed for `ko`, which builds Go binaries directly into container images.

### Build and push

```bash
cd go-app
export KO_DOCKER_REPO=myregistry.azurecr.io/talk-14
ko build .
```

What `ko` does:
- Compiles the Go app directly
- Builds a container image without a Dockerfile
- Often uses tiny distroless-style base images
- Pushes straight to a registry

### Local build without push

```bash
ko build --local .
```

Why teams like `ko`:
- Excellent for Go microservices
- Minimal image size and attack surface
- Reproducible builds with less boilerplate than Dockerfiles

## Alternative tool: Jib for Java

The `java-app` project uses the Jib Maven plugin.

### Run locally

```bash
cd java-app
mvn spring-boot:run
```

### Build an image with Jib

```bash
mvn compile jib:dockerBuild
```

### Push directly to a registry

```bash
mvn compile jib:build
```

Why Jib stands out:
- No Docker daemon required for registry builds
- Layering is optimized for Java dependencies vs app classes
- Fits well into Maven and Gradle workflows

## Alternative tool: Nixpacks

The `node-app` and `ruby-app` both work well as Nixpacks demos.

### Build the Node app

```bash
cd node-app
nixpacks build . --name node-nixpacks
```

### Preview the generated plan

```bash
nixpacks plan .
```

Why Nixpacks is interesting:
- Automatically detects many languages/frameworks
- Feels similar to classic Heroku build workflows
- Good developer convenience for prototypes and internal platforms

## Comparison commands

### Traditional Dockerfile for Ruby

```bash
cd comparison
cp Dockerfile.ruby ../ruby-app/Dockerfile
cd ../ruby-app
docker build -t ruby-sinatra-dockerfile .
```

Use this to compare:
- Dockerfile maintenance burden
- Image size
- Layer structure
- Manual vs automatic hardening

### Useful inspection commands

```bash
docker images
pack inspect-image ruby-sinatra-app
ko build --local .
mvn -q compile jib:_skaffold-files-v2
nixpacks plan .
```

What to point out:
- Which tools require Docker
- Which tools generate minimal images
- Which tools integrate supply chain metadata automatically

## When to use each tool

### Use a Dockerfile when you need
- Full control over every build step
- Custom OS packages or unusual runtime behavior
- Multi-stage logic that does not fit higher-level tools

### Use Buildpacks when you need
- Enterprise standardization
- Consistent secure defaults across many apps
- Easy onboarding for common stacks like Ruby, Node, Java, and .NET
- Rebase and SBOM support out of the box

### Use `ko` when you need
- The cleanest workflow for Go services
- Very small images
- No Dockerfile maintenance

### Use Jib when you need
- Strong Java/Maven or Gradle integration
- Layer-aware JVM image creation
- Direct registry builds from CI without Docker

### Use Nixpacks when you need
- Fast developer experience
- Automatic detection across varied stacks
- A platform-style build workflow without writing Dockerfiles first

## Key takeaways

- Dockerfiles are flexible, but flexibility often creates repetition and inconsistency
- Cloud Native Buildpacks provide a standard lifecycle for turning source code into OCI images
- `pack build` is the easiest way to demo buildpacks locally
- Builder images encode opinions and defaults from different ecosystems
- `pack rebase` is a powerful security and operations story
- SBOMs are a built-in advantage of buildpack workflows
- `ko`, Jib, and Nixpacks each remove Dockerfile work in stack-specific ways
- The best tool depends on whether you value control or convenience more

## Bonus topics

### Reproducible builds
Higher-level build tools usually produce more repeatable images because they standardize:
- base image selection
- dependency installation
- layer ordering
- metadata generation

### Custom buildpacks
If the default buildpacks are not enough, teams can add custom buildpacks to handle:
- internal CA certificates
- organization-specific agents
- custom startup logic
- shared build conventions

### `pack rebase` revisit
Rebase is worth emphasizing twice in the talk because it changes the patching story:
- security updates can be faster
- app rebuilds may be unnecessary
- platform teams can patch fleets more consistently

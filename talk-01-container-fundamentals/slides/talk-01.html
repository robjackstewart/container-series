Containers, from
first principles

A container is not a small virtual machine. It is a process, with its dependencies packaged alongside it, and a few kernel features drawing a boundary around it. Everything else in this talk follows from that one sentence.

The route

Nine steps, and the boundary matters every time

1

Section one

Containers are packaged
processes, not tiny VMs

If you take the VM analogy too literally, everything else in the talk lands wrong — image size, boot time, isolation, debugging. So let's fix the model first.

The difference is one whole row

A VM virtualises hardware. A container isolates a process.

Cue · say the trade-off out loud: a shared kernel means a kernel-level escape is a shared risk. When you need a hard boundary — untrusted code, strict regulatory separation — a VM is still the right tool. Containers are a packaging and density win, not a security upgrade.

There is no container object in Linux

"Container" is a name for two kernel features used together

The distinction that explains most operational confusion

An image is inert data. A container is a running process.

Image

A noun. Layers plus a config blob, addressed by digest. Immutable. Pull it, sign it, scan it, ship it.

Container

A verb. That image, plus a writable layer, plus runtime configuration, plus a process the kernel is actually running.

Why it matters

"It works on my machine" usually means the image is fine and the runtime configuration differs. Knowing which half to look at saves the afternoon.

Section two

Who actually does the work
when you type docker build

Not your shell. That single fact explains the build context, the layer cache, and the failure we are going to walk into deliberately in section 3a.

Three moving parts, one of which is not on your machine

The CLI asks. The daemon builds. The registry stores.

That trailing dot is a parameter, not punctuation

The build context is what you send, minus what you exclude

Cue · ask the room: if .dockerignore vanished from your current project, what would end up inside the build context? Most people find a .env, a private key, or a 400 MB node_modules they had forgotten about.

3

Section three

A readable, useful,
deliberately imperfect Dockerfile

We will build the naive version first, on purpose. It works, the mechanics are all visible, and every flaw in it becomes a lesson later in the talk.

Seven instructions · Dockerfile

Choose a base, add your code, say how to start it

# syntax=docker/dockerfile:1 FROM mcr.microsoft.com/dotnet/sdk:8.0 WORKDIR /workspace # convenient, but not cache-friendly — # any source edit invalidates the restore below COPY src/. ./src/ RUN --mount=type=secret,id=netskope_cert <<'EOF' …trust the corporate CA for this step only… dotnet restore "src/WeatherApi.csproj" …then remove it again… EOF RUN dotnet publish "src/WeatherApi.csproj" \ -c Release -o /app/publish --no-restore ENV ASPNETCORE_URLS=http://+:8080 EXPOSE 8080 ENTRYPOINT ["dotnet", "/app/publish/WeatherApi.dll"]
  • FROMThe starting filesystem. Everything it contains, you inherit — including its certificate trust store.
  • WORKDIRSets the directory for later instructions. Mostly metadata.
  • COPYMoves files from the build context into the image. Cannot reach outside it.
  • RUNExecutes a command inside a throwaway container and keeps the resulting filesystem changes.
  • ENVWrites a variable into the image config. The process sees it at run time.
  • EXPOSEDocumentation for humans and tooling. Opens nothing.
  • ENTRYPOINTThe process the container exists to run.
Be honest about this one

It works, and we would not ship it. The SDK, the compiler, the NuGet cache and the source tree all end up in the final image — 1.27 GB of it. Section 6 fixes that.

Cue · the --mount=type=secret on the RUN line is the next section. Do not explain it yet — build without it first and let the room watch it fail. If someone asks, that is even better: park it and say you will earn the answer in two slides.

Section three, continued

The same command. Your terminal:
fine. Inside RUN: broken.

Behind a TLS-intercepting proxy, this build fails. Why it fails is the whole of section 2 restated — and it is the fastest way to see where a build step actually runs.

Cue · set this up as a puzzle and reveal nothing yet. State that dotnet restore works in your terminal and fails inside the builder, ask the room why, and let them sit with it. This is the most useful five minutes in the talk — do not rush it.

Identical command · identical project · opposite outcomes

RUN is not your shell. It has its own trust store.

And NU1301 is a misleading error message

It reached nuget.org. It refused the certificate.

Demo 2 · five beats

Break it, diagnose it, prove the cause, fix it, prove the fix is clean

1

Build with no certificate. It fails.

PS> docker build --no-cache -t weatherapi:nocert -f .\Dockerfile . error NU1301: Unable to load the service index for source https://api.nuget.org/v3/index.json
2

Narrow it down inside the same base image. Is it the network, or the certificate?

PS> docker run --rm mcr.microsoft.com/dotnet/sdk:8.0 curl -sS https://api.nuget.org/v3/index.json curl: (60) SSL certificate problem: self-signed certificate in certificate chain ↑ it connected. It refused the certificate. Different problem.
3

Same container, same command — now with the CA mounted in. This is the controlled experiment: one variable changed.

PS> docker run --rm -v "${PWD}\certs\netskope.crt:/usr/local/share/ca-certificates/netskope.crt:ro" ` mcr.microsoft.com/dotnet/sdk:8.0 sh -c "update-ca-certificates && curl -sS https://api.nuget.org/v3/index.json" Updating certificates in /etc/ssl/certs... 1 added, 0 removed; done. Running hooks in /etc/ca-certificates/update.d... done. { "version": "3.0.0", "resources": [ { "@id": "https://azuresearch-usnc.nuget.org/query", … ↑ nuget.org answers. Nothing changed but the trust store.
4

Now do the same thing in the build — deliberately, for one step only.

PS> docker build --secret id=netskope_cert,src=.\certs\netskope.crt -t weatherapi:single -f .\Dockerfile . => [5/6] RUN --mount=type=secret,id=netskope_cert DONE
5

Prove the certificate did not contaminate the image.

PS> docker run --rm --entrypoint sh weatherapi:single -c "ls -A /usr/local/share/ca-certificates/ | grep -i netskope; ls -A /run/secrets" no netskope.crt in image no /run/secrets in image ← verified on this machine today

Cues · Beat 1: ask the room why before you say anything. Beat 3: this is the beat that settles it — the certificate was the only missing piece, and you proved it without touching the Dockerfile. Beat 5: "trust me, it's clean" is not an engineering standard, so show it. The rehash: warning line in beat 3 is harmless noise from update-ca-certificates reading the existing bundle — mention it only if someone asks.
--no-cache in beat 1 is mandatory. A secret mount's contents are not part of the layer cache key — only the declaration is. With a warm cache the build succeeds without the cert and spoils the whole demo. Off the corporate network? Beats 1–3 all simply pass; narrate the expected output rather than faking a failure.

Where does the certificate end up?

Three ways to fix it. Two of them ship your CA to strangers.

Cue · worth flagging for later — Buildpacks, ko, jib, Nixpacks and Aspire have no equivalent of --mount=type=secret — they need the CA trusted at host level instead. Talk 14 hits that properly.

One non-obvious mechanic that will eventually bite you

A secret's contents are not part of the cache key

Why that is good

Only the declaration of the mount is hashed, not the file. So the same Dockerfile stays cacheable across machines whose certificates differ — yours, your colleague's, CI's.

Why that will confuse you

After one successful build, rebuilding without --secret reports CACHED and succeeds with no certificate at all. The build looks like it never needed one.

So, when demonstrating

Always --no-cache. And you cannot use a secret mount to deliberately invalidate cache — it has no effect on the key.

# after a successful build, drop the secret: PS> docker build -t weatherapi:single -f .\Dockerfile . #10 [4/6] RUN --mount=type=secret,id=netskope_cert … #10 CACHED # …succeeds. No certificate was involved. # The layer was already built and its key did not change. # which is why beat 1 of the demo needs: PS> docker build --no-cache …

Cue · debugging note for this repo: if a heredoc build dies with /bin/sh: 1: set: Illegal option - that is CRLF line endings, not certificates — it fails before any network call, so rule it out first.

A layer is a diff, not a directory

You can add a file in a later layer. You cannot un-add one.

You change one line of C#. What has to be redone?

Section five

What is decided when
you build, and what waits

Four mechanisms, one boundary. Getting these confused is how credentials end up in images and how "it works in dev" becomes a deployment incident.

Follow APP_VERSION across the boundary

ARG is build input. ENV is image config. -e wins at run time.

Cue · call back to demo 1 — /info reported version: dev when we ran it with plain dotnet run. After the multi-stage build it will report 1.0.0 — stamped at build time — and docker run -e APP_VERSION=2.0.0 will override it without touching the image.

6

Section six · the payoff

Build with the toolchain.
Ship without it.

One Dockerfile, two FROM lines. Compilation happens in an image that has a compiler; execution happens in an image that has only a runtime. For compiled languages this is simply the normal shape.

One arrow crosses. Everything else is thrown away.

The build stage is scaffolding, not cargo

Same application · same endpoints · measured on this machine today

1.27 GB becomes 324 MB for eleven extra lines

Operations

950 MB less to push, pull, cache on every node and store in every registry — on every deploy, forever.

Security

No compiler, no package manager, no git, no curl in production. Fewer packages to scan and far less for an attacker to work with. And USER app means the process is not root.

The honest caveat

Smaller is not automatically secure. The useful question is "does the final image contain only what this process needs to run?" — not "how few megabytes can I get to?"

Build the multi-stage image, then put them side by side

PS> docker run --rm -d --name weatherapi-multi -p 8080:8080 ` -e ASPNETCORE_ENVIRONMENT=Production weatherapi:multi PS> Invoke-RestMethod http://localhost:8080/info app : Weather API version : 1.0.0 ← stamped by --build-arg at BUILD time environment : Production
PS> docker image ls weatherapi REPOSITORY TAG SIZE weatherapi single 1.27GB weatherapi multi 324MB # and the run-time override, no rebuild: PS> docker run --rm -e APP_VERSION=2.0.0 -p 8081:8080 weatherapi:multi version : 2.0.0

Section seven · faster feedback without fatter images

Keep the package cache beside the build, not inside the image

Straight with you

Neither Dockerfile in this talk uses a cache mount — they were kept simple on purpose. This is the next improvement, not something already in the code.

What it actually buys

In the multi-stage build the restore layer is discarded anyway, so a cache mount buys build speed, not a smaller image. In the single-stage build it would also remove those 41.8 MB from the shipped result.

Why the syntax line matters

# syntax=docker/dockerfile:1.7 at the top of the file is what makes these mount options available. BuildKit is the default builder in modern Docker Desktop.

The close

Eight things to leave with

  • 01A container is a process with packaged dependencies, sharing the host kernel — not a small VM.
  • 02An image is inert data; a container is that image plus runtime configuration plus a running process.
  • 03RUN executes inside the image — its network, filesystem and CA trust store are the base image's, never yours.
  • 04Build-time secrets belong in --mount=type=secret. Never a COPY, never an ARG.
  • 05Ordering matters because cache keys are content-sensitive and the first miss invalidates everything after it.
  • 06ARG is build input; ENV and docker run shape runtime behaviour.
  • 07.dockerignore is a security and performance control, not housekeeping.
  • 08Multi-stage is the normal shape for compiled apps — and USER app is a one-line security win.
If only one sentence survives the week

Container quality is about boundaries: what enters the build context, what becomes a layer, what crosses into the final image, and what is supplied at run time. Every question in this talk was one of those four.
